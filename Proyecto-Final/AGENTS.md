## 2. Reglas de commits

- **Conventional Commits SIN scopes.**
- Mensajes en **ingles, minusculas, sin punto final**.
- Tipos validos: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `release`, `hotfix`.
- Un commit = un cambio logico. No mezclar refactor con feature.
- **Prohibido atribuir IA** en commits (`Co-Authored-By: Claude`, `Generated by ...`, etc.).

Validacion: `commitlint` corre en cada PR. Falla = PR bloqueado.

Ejemplos OK:

```
feat: add login screen
fix: resolve token expiration bug
docs: update database setup guide
```

Ejemplos malos:

```
feat(auth): add login            # tiene scope
Feat: add login                  # mayuscula
feat: add login.                 # punto final
update                           # tipo invalido + vago
```

## 3. Reglas de ramas — Git Flow

- **Nunca** commit directo a `main` ni `develop` (branch protection lo bloquea de todas formas).
- Crea rama segun tipo:
  - `feature/*` — funcionalidad nueva, nace de `develop`
  - `bugfix/*` — bug no urgente, de `develop`
  - `chore/*` — mantenimiento, de `develop`
  - `docs/*` — solo docs, de `develop`
  - `test/*` — pruebas tecnicas, de `develop`
  - `hotfix/*` — urgente en prod, de `main`
  - `release/*` — preparar version, de `develop`
- Nombres en kebab-case: `feature/database-schema-init`, `bugfix/fix-jwt-expiration`.
- PR siempre hacia `develop` (excepto `hotfix/*` y `release/*` que van a ambos).

## 8. Prohibido

- Implementar codigo de otros modulos sin que el owner lo apruebe.
- Commitear lockfiles `package-lock.json` ni `yarn.lock` (`.gitignore` los bloquea).
- Commitear archivos Office (`.htm`, `.doc`, `.docx`).
- Modificar talleres ya entregados sin instruccion explicita.
- Crear archivos en raiz del repo o raiz de `Proyecto-Final/` (van dentro de un modulo).
- Saltarse el CI con `--no-verify` y push directo — branch protection lo bloquea de todas formas, pero ni intentes.
- Hardcodear credenciales, secrets o URLs de produccion. Usa `environment.ts` / `.env`.
